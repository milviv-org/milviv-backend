# 2. Архитектурные ограничения

Архитектурные ограничения определяются не только требованиями к самой системе, но и учебными и организационными целями проекта.

## 2.1 Учебные ограничения

| ID    | Ограничение                                                                                                      | Последствие                                                                                                                                    |
| ----- | ---------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| LC-01 | Серверная часть системы должна быть реализована на Java.                                                         | Архитектура backend должна учитывать возможности стандартной Java и используемых низкоуровневых библиотек.                                     |
| LC-02 | Не допускается использование высокоуровневых backend-фреймворков, таких как Spring.                              | Значительная часть инфраструктурной логики должна быть реализована самостоятельно.                                                             |
| LC-03 | Реализация должна позволять автору изучать внутренние механизмы, которые обычно скрываются backend-фреймворками. | Архитектура должна избегать необоснованного использования готовых абстракций, если их самостоятельная реализация является частью учебной цели. |

Основная цель ограничений — получение практического опыта разработки серверных приложений на Java и понимание механизмов, которые обычно предоставляются готовыми фреймворками. Но цель продука важнее чем цель обучения. Обучение не должно приводить к больгим увеличениям срока разработки

## 2.2 Организационные ограничения

| ID    | Ограничение                                                                               | Последствие                                                                                                                                         |
| ----- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| OC-01 | Исходный код проекта должен быть открытым.                                                | Код, документация и архитектура должны быть пригодны для публичного просмотра. Секреты и конфиденциальные данные не должны храниться в репозитории. |
| OC-02 | Архитектура и ключевые решения должны быть документированы непосредственно в репозитории. | Документация должна храниться рядом с исходным кодом и развиваться вместе с системой.                                                               |

## 2.3 Соглашения разработки

| ID    | Соглашение                                                                         | Последствие                                                                      |
| ----- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| CV-01 | Коммиты должны описывать конкретное логическое изменение.                          | История Git должна оставаться понятной и пригодной для анализа развития системы. |
| CV-02 | Для коммитов используются префиксы `feat`, `fix`, `refactor`, `test`, `perf`.      | По истории Git можно определить характер внесённого изменения.                   |
| CV-03 | Один коммит должен по возможности представлять одно логически связанное изменение. | Упрощается анализ истории, поиск изменений и откат отдельных изменений.          |
