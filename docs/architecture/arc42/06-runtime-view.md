# 6. Рабочие сценарии

Два сценария, наиболее показательных для архитектуры. Остальные следуют тем же правилам.

6.1 реализован (`CompleteTask`), 6.2 — целевое поведение.

---

## 6.1 Выполнение задачи → начисление баллов

Главный сценарий системы. Показывает границу транзакции и механизм QG-03.

```
Контроллер                Сценарий (application)         БД
    │                            │                        │
    │ POST /tasks/{id}/complete  │                        │
    ├───────────────────────────►│                        │
    │                            │ ── открыть транзакцию ─┤
    │                            │                        │
    │                            │ 1. загрузить задачу    │
    │                            │    (с версией)         │
    │                            │ 2. отметить выполненной│
    │                            │ 3. записать факт       │
    │                            │    выполнения (история)│
    │                            │ 4. начислить баллы     │
    │                            │    в points_history    │
    │                            │                        │
    │                            │ ── commit ─────────────┤
    │◄───────────────────────────┤                        │
```

Существенное:

* шаги 2–4 атомарны — иначе задача закрыта, а баллы не начислены (QG-03);
* `UPDATE` задачи содержит версию в `WHERE`; при конфликте — `OptimisticLockException`, и `RetryableTransactionManager` повторяет транзакцию целиком (AR-01);
* шаг 3 пишет append-only запись: план, факт, сложность, баллы (QG-04);
* баланс не хранится отдельным изменяемым полем — источник правды `points_history` (AD-16).

## 6.2 AI-запрос → предложение → подтверждение

Показывает, почему внешний вызов находится вне транзакции и почему создание разделено на две фазы.

```
Клиент          Сценарий            Gemini            БД
  │ сообщение      │                  │                │
  ├───────────────►│ текст            │                │
  │                ├─────────────────►│                │
  │                │◄─ запрос данных ─┤                │
  │                │ ── чтение (WHERE user_id) ───────►│
  │                │ данные           │                │
  │                ├─────────────────►│  (секунды)     │
  │                │◄─ предложение ───┤                │
  │                │ валидация, сохранение предложения │
  │◄─ предпросмотр ┤                  │                │
  │ подтверждение  │                  │                │
  ├───────────────►│ ── транзакция: создать всё ──────►│
  │                │ ── commit ───────────────────────►│
  │◄───────────────┤                  │                │
```

Существенное:

* команды пользователя нет; AI сам запрашивает нужные данные из закрытого каталога, сервер отдаёт только данные текущего пользователя (AD-15, QG-01);
* ответ AI валидируется тем же механизмом, что и пользовательский ввод (AD-10);
* сущности создаются только после подтверждения, одной транзакцией — всё или ничего;
* транзакция открывается **после** ответа Gemini — иначе соединение из пула удерживалось бы всё время сетевого вызова (AD-08).
