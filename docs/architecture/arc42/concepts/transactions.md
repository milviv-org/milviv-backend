Транзакция - это операция в котором будет выполнена все или нечего, если в процессе операции, вызывалась ошибка, то транзакция завершается и считается не выполненной.

Например в случае с базой данных, если открыть транзакцию и в процессе транзакции изменять данные в таблицах и закрыть ее, но в процессе была ошибка, то данные успевшие изменится не применяются. Это сделано для того, что бы сохранить консистентность данных.

Пример:

// BAD

taskRepository.doneTask(task);
pointsRepository.addPoints(20); // упало(в итоге задача закрыта, но баллы не начислились)

// GOOD

transaction.execute(() => {
  taskRepository.doneTask(task);
  pointsRepository.addPoints(20); // упало

  // задача не будет выполнена, так как балы не начислены
})

ConnectionHolder - класс содержит текущее соедениние с БД в потоке. Каждый запрос имеет свой поток.
ConnectionProvider - класс для передачи текущего соединения с БД. Использует ConnectionHolder.

Необходим что бы не прокидовать Connection через ииерархию класса вручную. ConnectionProvider зарегистрирован в DIContainer и легко будет доступен в любом месте.

JdbcTransactionManager - главная логика управления транзакцией, который автоматизирует commit/rollback/connection clear. Это удобный инструмент, через который можно безопастно изменять данные в БД. Реализует интерфейс TransactionManager (application layer). Имеет гибкий метод execute с перегрузками: (Runnable), (Supplier), (Propagation, Supplier) и (Propagation, IsolationLevel, Supplier).

action - производимое действие с БД
Propagation - влияет на распространение транзакции
  REQUIRED - присоеденяется к текущей транзакции, если нету, то создает новую
  REQUIRES_NEW - всегда создает новую транзакцию, отключает временно текущую транзакцию(если есть), и обратно вернет после новой транзакции
  MANDATORY - всегда требовать транзакцию, если нет активной — бросает IllegalStateException
  SUPPORTS - использует транзакцию если есть, без неё тоже работает. Подходит для read-only операций
IsolationLevel -  уровень изоляции данных БД во время транзакции
  READ_COMMITTED - видеть закомиченные данные(95% всех операции)
  REPEATABLE_READ - при повторном чтении гарантирует, что значение будет той же при первом чтении. В основном если нужна стабильность данных, например при генерации отчета с суммированием, что бы сумма не съехалась, где не критичны актуальность данных
  SERIALIZABLE - БД гарантирует, итог эквивалентный последовательному выполнению транзакции, но на самом деле может их паралельно запускать и отменять конфликтующие. Используются в случае, где критична гонка данных. Например при работе с деньгами.

Пример бронирования места, где isolationLevel = SERIALIZABLE

transactionManager.execute(Propagation.REQUIRED, IsolationLevel.SERIALIZABLE, () -> {
  // общее количество мест
  int total = bookings.countSeats()
  // количество занятых мест
  int taken = bookings.countBookings()

  // если мест нету
  if (taken >= total) {
    throw new Exception("Нет мест");
  }

  // успешное бронирование
  Booking booking = bookings.create(flightId, userId);
  bookings.save(booking);
  return booking;
}) 

Тут без IsolationLevel.SERIALIZABLE есть возможность на последнее место бронировать несколько мест из за паралельности запроса. С IsolationLevel.SERIALIZABLE такого быть не может, так как он гарантирует, итог эквивалентный последовательному выполнению транзакции, но на самом деле может их паралельно запускать и отменять конфликтующие. 

RetryableTransactionManager - имплементируется от интерфейса TransactionManager и оборачивает JdbcTransactionManager (декоратор), его ответственность повторно отправить запрос транзакции, в случае временных ошибок. Под временными ошибками имеется ввиду ошибки, которые вызваны не логической ошибкой. Например Ошибка 40001 (serialization failure), Deadlock (40P01) или OptimisticLockException. Если он видит что ошибка одна из них, то повторно выполняет транзакцию, при этом не выполняет сразу, а через некоторый таймаут(если отправлять сразу, почти гарантированно будет та же ошибка). Также если у нас 10 паралельных запрос, где каждый их них вызывает ошибку serialization failure, таймаут может не помочь, если у каждого из них один и тот же таймаут, в этом случае, все они обратно будет выполняться паралельно. Что бы избежать такого поведения, реализован exponential backoff + equal jitter: базовая пауза 50мс удваивается с каждым ретраем (50 → 100 → 200мс...) с потолком 1000мс, при этом половина паузы фиксированная, а вторая половина — случайная. Backoff дает конфликтующей транзакции время завершиться, а jitter разносит повторы конкурирующих потоков по времени. В таком случае риск паралельности меньше.

OptimisticLock - подход для обнаружения, что данные были изменены в рамках одной таблицы БД, что может помочь защитить от lost_update, когда есть гонка данных. Реализуется это с помощью добавления колонки версии в таблицу. Если есть несколько парелельных запросов, с помощью специфичной SQL query можно защитить изменения данных.

Например у нас есть некоторый общий счетчик, пришли 2 паралельных запроса от разных пользователей, где каждый запрос должен поменяться таким образом, что первый запрос должен добавить в счетчие 20, а второй 50.

1 запрос
UPDATE counter
SET count = ?,
    version = version + 1
WHERE company_id = 1
AND version = 1

Где в ? будет передан count + 20

2 запрос
UPDATE counter
SET count = ?,
    version = version + 1
WHERE company_id = 1
AND version = 1

Где в ? будет передан count + 50

Представим что count до запросов был равен 100

В таком случае выполнится только 1 запрос гарантированно, а 2-й не выполнится гарантированно. Не выполнившийся запрос, может прочесть результат, и если он не смог изменить данные, то может бросить OptimisticLockException
Также с retry механизмом он отловит OptimisticLockException, транзакция может повторится и выполнится 2 запрос, где уже обновленный счетчик после 1 запроса, таким образом будет сохранена консистеность данных и счетчик в этом случае будет равен 170.

Если не использовать этот подход, то консистеность данных была бы нарушена, то счетчик был бы равен последнему отработанному запросу, либо 120, либо 150

Также подход OptimisticLock считается производительным, так как он не блокирует физический БД для изменение данных.

Можно придумать другой пример, например 2 пользователя паралельно отправили запрос на измение одно и того же файла, бизнес логика должна быть такой, в случае если несколько пользователей одновременно изменили файл, то должно примениться первое измененное, а остальным пользователем должно быть сообщено, что файл уже был изменен другим пользователем. В таком случае можно применить OptimisticLock

VersionedAggregate - абстрактный базовый класс для агрегатов с optimistic locking. Его единственная ответственность - хранить версию агрегата и синхронизировать её in-memory состояние с БД. Агрегат(например User) наследуется от него и получает поле version, которое репозиторий использует в WHERE clause при UPDATE, а при несовпадении версии бросает OptimisticLockException.

Важный контракт: incrementVersion() вызывается ТОЛЬКО из репозитория после успешного UPDATE. Domain и Application слои версией не управляют - иначе объект в памяти рассинхронизируется с БД и следующий save() даст ложный OptimisticLockException, либо наоборот пропустит реальный конфликт.
