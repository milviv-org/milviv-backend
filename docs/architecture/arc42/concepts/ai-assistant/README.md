# AI Assistant: взаимодействие backend ↔ AI

> **Статус: принято** (2026-09-27). Итоговое архитектурное решение по AI Assistant. Код ещё не реализован: после реализации документ сверяется с кодом.

**Метки:**
- **[Ф]** — факт из документации MILVIV или кода;
- **[Р]** — решение владельца продукта;
- **[Т]** — требование из постановки задачи;
- **[П]** — решение, предложенное при проектировании и **принятое вместе с документом**;
- **[TO]** — trade-off;
- **[Д]** — допущение безопасности.

Числа в лимитах — принятые **значения по умолчанию**; меняются через конфиг ([§8](limits-and-security.md)).

**Термины:**
- **Предложение** — то, что AI хочет сделать: создать, изменить, удалить. **Создания выполняются сразу** [Р G-25]. Изменения и удаления ждут подтверждения пользователя.
- **Предпросмотр** (= **карточка подтверждения**, G-10) — список **изменений и удалений**, которые предлагает AI, в сообщении AI в чате. У каждой операции тип и название сущности, без деталей, и пустая галочка. Кнопки «Выполнить отмеченное» / «Отклонить». Если AI предложил только создания, карточки нет.
- **Отчёт** — список сущностей, которые реально созданы, изменены, удалены, со ссылками на них (G-21). Без описания, что именно изменилось.

## 1. Problem statement

Пользователь пишет свободный текст:
- «Хочу выучить английский»;
- «Перенеси все задачи по грамматике на неделю»;
- «Удали проект „Старый“»;
- «Какие задачи я чаще всего просрочиваю?».

AI определяет намерение, при необходимости **явно запрашивает** данные пользователя, а затем:
- **предлагает** создать, изменить и удалить сущности (Goal, Project, Task, Reward);
- или отвечает текстом;
- или задаёт уточняющий вопрос.

При этом:
- выход AI — **недоверенные данные** [Т];
- ни один ответ AI, даже самый враждебный, не должен:
  - прочитать чужие данные, скрытые награды или больше, чем разрешает каталог;
  - изменить или удалить что-либо **без согласия пользователя на эту конкретную операцию**;
  - выйти за серверные лимиты.

**Критерий проверки архитектуры:** считаем, что атакующий полностью управляет ответами модели. Худший исход:
- (а) модель прочитала данные **самого пользователя** из каталога в пределах лимитов;
- (б) создано ≤ 40 новых сущностей в аккаунте пользователя (он увидит их в отчёте и может удалить);
- (в) появилось предложение из ≤ 30 изменений и удалений, в котором каждая сущность названа и не будет затронута без отдельной галочки.

## 2. Architectural principles

1. **AI — источник данных, не исполнитель.** Запрос данных — *просьба*, которую сервер исполняет или отклоняет. Предложение — *черновик*: сервер его проверяет и только потом исполняет создания сам, а изменения и удаления откладывает до подтверждения.
2. **Разрушительное — только по явному согласию** [Р G-3, G-25]. Создание ничего не портит, поэтому выполняется сразу. Изменение и удаление исполняются, только если пользователь **перечислил** их в подтверждении. Согласие проверяет сервер, а не только интерфейс.
3. **Названия сущностей — из БД, а не из текста AI.** В карточке и отчёте сервер показывает список затронутых сущностей по их реальным данным (тип, название, ID для ссылки). Деталей изменений нет [Р G-21]. Текст модели показывается только как пояснение.
4. **Данные только по явному запросу** [Р G-7] из закрытого каталога, только текущего пользователя, без скрытых наград.
5. **Нет отдельного пути записи и чтения для AI.** Когда пользователь создаёт задачу кнопкой в интерфейсе, сервер вызывает прикладной сценарий `CreateTask`, и в нём проверяются все правила: длина названия, баллы ≤ 1000, срок задачи ≤ срока проекта и т. д. Когда задачу создаёт предложение AI, вызывается **тот же** `CreateTask` — не отдельный «AI-код», пишущий в БД напрямую. Поэтому правила существуют в одном месте и не могут разойтись, а AI физически не может сделать то, чего нельзя сделать вручную (например, выполнить задачу, если такого сценария для AI нет, или записать задачу чужому пользователю). То же для чтения: каталог данных использует те же репозитории с фильтром по пользователю.
6. **Закрытый контракт.** Неизвестное поле, операция, тип запроса или значение enum → отказ. Никаких `Map<String, Object>` [Т].
7. **Лимиты — в коде, не в промпте.**
8. **Модель не видит ID.** Только дескрипторы, выданные в этом запросе ([§6.4](contract.md)).
9. **Провайдер заканчивается в адаптере.**
10. **Пользователь всегда знает, что сделано** [Р G-21]. После исполнения — отчёт по каждой операции, построенный сервером по фактическому результату.
11. **Без согласия на использование данных AI недоступен** [Р G-12]. Проверяет сервер, а не только фронтенд.

## 3. Trust boundaries

```
  ┌──────────── недоверенное ────────────┐     ┌──────────── доверенное ─────────────┐
  │ текст пользователя                    │ ──► │ presentation → application → domain │
  │ ответ AI: запросы данных, план, текст │ ──► │ БД, конфиг лимитов, каталог данных, │
  │ данные пользователя, отданные AI      │     │ шаблоны промптов, дескрипторы,      │
  │ (могут содержать хранимую инъекцию)   │     │ сохранённый план и версии сущностей │
  └───────────────────────────────────────┘     └─────────────────────────────────────┘
          TB-1: клиент → API          TB-2: сервер ⇄ провайдер AI
```

- **TB-1.** Пользователь аутентифицирован, но его ввод недоверенный. Подтверждение — это тоже ввод, поэтому сервер проверяет, что подтверждены только операции этого плана.
- **TB-2, исходящее направление** — граница конфиденциальности. Через неё уходят данные из БД. [Р G-8] Тариф бесплатный: по моим сведениям, на нём провайдер может использовать данные для улучшения своих продуктов. **Принятый риск**; текст окна согласия (G-12) должен об этом сообщать. Формулировку сверить с условиями Google.
- **TB-2, входящее направление** — граница целостности. Ответ AI доверен меньше, чем ввод пользователя.
- **Данные, отданные AI**, становятся частью промпта. Название задачи или ответ рефлексии могут содержать текст-инструкцию (хранимая инъекция). Опасное последствие — предложение удалить данные — закрыто принципом 2.
- **Системный промпт не секрет** [Ф OC-01].

## 17. Final architecture

```
presentation   AiConsentController: GET/POST /api/ai/consent
               AiRequestController: POST /api/ai/requests · POST /{id}/execution · POST /{id}/rejection
                   │  userId только из токена (rest/filters, D-01)
application    HandleAiRequest                                   ExecuteAiPlan
                 1 согласие, квоты, предохранитель,                1 загрузка WHERE user_id, TTL, статус
                 2 цикл ≤ 2 раундов:                               2 решение: approvedChangeIds
                     AiAssistantPort → AiTurn                        (изменения/удаления — только явные)
                     DATA_REQUEST → AiPolicy → AiDataCatalog       3 версии целей = снимок, иначе 409
                       (user_id, без скрытых наград, дескрипторы)  4 Create* → Update* → Delete* (ручные)
                 3 PROPOSAL → Validator + Policy                   5 → EXECUTED, отчёт, audit_log
                 3a создания → ExecuteAiPlan сразу (tx), отчёт
                 4 PreviewBuilder (список затронутых)         одна транзакция, всё или ничего
                 5 сохранить AiRequest (PROPOSED)
domain         AiRequest (состояния, решение, версия) · ValidatedPlan · Goal/Project/Task/Reward
infrastructure GeminiAssistantAdapter (многоходовый HTTP, схема, таймауты, ретраи, квота, строгий разбор)
               AiRequestJdbcRepository · JdbcTransactionManager/Retryable [Ф] · миграции [§6.9](data.md)
test           FakeAiAssistant · записанные ответы Gemini · заглушка HTTP
```

**Инварианты реализации:**
1. Выход AI → только `AiTurn` → только через валидатор.
2. Данные AI получает только по проверенному каталожному запросу, только текущего пользователя, **никогда — скрытые награды**.
3. Модель не видит ID.
4. Создания исполняются сразу после проверки; изменение и удаление — только если перечислены в подтверждении пользователя и цель не изменилась с момента предпросмотра.
5. Без согласия на использование данных AI не вызывается.
6. Отчёт об операциях строится из фактического результата, а не из текста AI.
7. Названия затронутых сущностей в карточке и отчёте — всегда из БД.
8. Все записи — в `ExecuteAiPlan`, одной транзакцией, через ручные сценарии.
9. Вызовы AI — вне транзакций; провайдерские типы — только в адаптере.

**Порядок реализации [П]:**
1. D-01;
2. миграции [§6.9](data.md);
3. ручные CRUD четырёх сущностей с правилами дат;
4. согласие на использование данных ([§6.10](user-flow.md));
5. `AiRequest` + fake + создание + отчёт;
6. каталог и дескрипторы;
7. изменения и удаления с предпросмотром и подтверждением;
8. адаптер Gemini;
9. квоты и предохранитель;
10. онлайн-прогон.
