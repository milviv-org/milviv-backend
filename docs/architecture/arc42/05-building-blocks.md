# 5. Строительные блоки

Статическая структура системы. Описана **целевая** структура; блоки, которых в коде ещё нет, помечены статусом.

**Статусы:** ✅ реализовано · 🟡 частично · ⚠️ не реализовано.

Механизмы (как работают DI, транзакции, валидация) — в разделе 8. Здесь только структура.

---

## 5.1 Уровень 1 — Слои

```
presentation  →  infrastructure  →  application  →  domain

                    shared  (доступен всем, не зависит ни от кого)
```

**Мотивация.** Без фреймворка (LC-02) границы приходится задавать явно, иначе SQL, HTTP и JSON проникают в прикладную логику и убивают независимое развитие областей (QG-05).

Зависимости однонаправлены и завершаются на `domain`. Интерфейс репозитория объявлен в `domain`, JDBC-реализация — в `infrastructure` (инверсия зависимостей).

| Блок | Ответственность | Статус |
| ---- | --------------- | ------ |
| `domain` | Сущности, правила предметной области, интерфейсы репозиториев, доменные исключения | 🟡 |
| `application` | Прикладные сценарии, границы транзакций | 🟡 |
| `infrastructure` | HTTP-сервер, маршрутизация, DI, доступ к БД, миграции, конфигурация | ✅ |
| `presentation` | HTTP-контроллеры, DTO, composition root | 🟡 |
| `shared` | Инструменты общего назначения, не связанные с предметной областью | ✅ |

**Критерий попадания в `shared`:** инструмент применим вне MILVIV и не упоминает доменные понятия. Валидация подходит — она не знает о задачах и баллах.

### Правила зависимостей

* `domain` не импортирует `application`, `infrastructure`, `presentation`;
* `application` импортирует только `domain` и `shared`;
* `infrastructure` реализует интерфейсы, объявленные в `domain` и `application`;
* `presentation` собирает граф зависимостей и не содержит прикладной логики;
* `shared` не импортирует ни один слой; любой слой может импортировать `shared`.

Правила следуют чистой архитектуре и DDD.

## 5.2 Уровень 2 — Внутри слоёв

### domain

Деление по предметным областям: каждая владеет своими сущностями и интерфейсом репозитория.

| Блок | Ответственность | Статус |
| ---- | --------------- | ------ |
| `user` | Пользователь, учётные данные, `UserRepository` | ✅ |
| `auth` | Refresh-токены сессий, `RefreshTokenRepository` | ✅ |
| `goal` | Цели (FR-01) | ✅ |
| `project` | Проекты, связь с целями, вычисляемая сложность (FR-02) | ✅ |
| `task` | Задачи, срок, сложность, факт выполнения, связь с проектом и целью (FR-03, FR-04) | ✅ |
| `planning` | Планы, история переносов, календарь (FR-05, FR-06) | ✅ |
| `gamification` | Баллы, баланс, награды, обмен, скрытые награды (FR-09…FR-11) | ✅ |
| `reflection` | Вопросы и ответы рефлексии (FR-12) | ✅ |
| `statistics` | Сводка по истории выполнения, прогресс проектов и целей (FR-07) | ✅ |
| `ai` | AI-запрос, план, согласие на использование данных (FR-13) | ⚠️ |
| `shared` | `VersionedAggregate` — версионирование агрегатов | ✅ |
| `exception` | `AppException` и наследники | ✅ |

**Границы областей.** Баллы и награды объединены в `gamification`: QG-03 требует их согласованности в одной транзакции, а граница транзакции не должна пересекать границу области. Цели и проекты разделены — каждая сущность может существовать без другой.

### application

Задаёт **границы транзакций**: транзакция открывается и закрывается в прикладном сценарии.

Граница на репозитории невозможна — выполнение задачи и начисление баллов атомарны (QG-03), а это два репозитория. Граница на контроллере отвергнута: обращение к Gemini (FR-13) удерживало бы соединение из пула секундами.

| Блок | Ответственность | Статус |
| ---- | --------------- | ------ |
| `transaction` | `TransactionManager`, `Propagation`, `IsolationLevel` | ✅ |
| Сценарии предметных областей | По одному пакету на область | 🟡 все, кроме ai |

### infrastructure

Всё, что предоставил бы фреймворк. Основная учебная ценность проекта (LC-03).

| Блок | Ответственность | Статус |
| ---- | --------------- | ------ |
| `container` | `DIContainer`, `@Inject`, `Scope` | ✅ |
| `http` | `JettyServer`, `HttpContext`, `ErrorMapper`, `HttpStatusResolver` | ✅ |
| `http/router` | `Router`, `RouterScanner`, `RouteHandler` | ✅ |
| `http/annotations` | `@Controller`, `@Get`, `@Post`, `@Put`, `@Patch`, `@Delete` | ✅ |
| `persistence` | Пул соединений, `ConnectionHolder`/`ConnectionProvider`, JDBC-репозитории, `JdbcTransactionManager`, `RetryableTransactionManager` | 🟡 |
| `migration` | `FlywayMigrationRunner` | ✅ |
| `config` | `ConfigLoader`, `AppConfig`, `JacksonConfig`, `ControllerRegistrar` | ✅ |
| `exception` | `DatabaseException`, `RouterConfigurationException` | ✅ |
| `logging` | Логирование | ⚠️ |

### presentation

Слой тонкий: принять запрос → преобразовать DTO → вызвать сценарий → вернуть DTO. Логика здесь — признак того, что её место в `application`.

| Блок | Ответственность | Статус |
| ---- | --------------- | ------ |
| `Main` | Composition root | ✅ |
| `rest/controllers` | `AuthController`, `GoalController`, `ProjectController`, `TaskController`, `PlanController`, `CalendarController`, `RewardController`, `PointsController`, `ReflectionController`, `StatisticsController`, `SoundSettingsController`, `HealthController` | 🟡 |
| `rest/dto` | Внешний контракт API отдельно от доменных сущностей | ⚠️ |
| Аутентификация | `@Public` + проверка токена в `RouterScanner` (`infrastructure/http`, `infrastructure/security`) | ✅ |
| `rest/exception` | Обработка исключений на границе HTTP | ⚠️ |


### shared

| Блок | Ответственность | Статус |
| ---- | --------------- | ------ |
| `validation/base` | Чистые правила проверки значения | ✅ |
| `validation/annotation` | Декларативная валидация: `@Required`, `@Email`, `@Min`, `@Max`, `@MinLength`, `@MaxLength`, `@Pattern`, `@EnumValue` | ✅ |
| `validation/complex` | Процедурная валидация для правил, зависящих от нескольких полей | ✅ |

## 5.3 Текущее состояние

Реализованы инфраструктурный слой и срезы: аутентификация, цели, проекты, задачи с начислением баллов, планирование и календарь, награды и баланс, рефлексия, статистика, звуки. Остальные предметные области существуют как решение о декомпозиции, зафиксированное выше.

Схема БД опережает код: миграции V1–V15 создают таблицы всех предметных областей, код есть у `users`, `refresh_tokens`, `goals`, `projects`, `tasks`, `plans`, `task_completions`, `task_reschedules`, `points_history`, `rewards`, таблицы рефлексии. Список таблиц и колонок — [database.md](../database.md).
