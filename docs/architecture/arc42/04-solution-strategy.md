# 4. Стратегия решения

Раздел фиксирует ключевые решения, определяющие облик системы, и связывает их с целями качества из раздела 1 и ограничениями из раздела 2.

## 4.1 Ключевые решения

Два решения определяют архитектуру MILVIV и объясняют большую часть остального кода.

### Слоёная архитектура без backend-фреймворка

Система разделена на четыре слоя с однонаправленной зависимостью:

```
presentation → infrastructure → application → domain
```

`domain` не зависит ни от одного другого слоя. Прикладная логика (`application`) не знает ни о HTTP, ни о JDBC. Технические детали сосредоточены в `infrastructure`, а обработка HTTP-запросов — в `presentation`.

Решение вытекает напрямую из LC-02 (запрет на Spring и аналогичные фреймворки): без фреймворка, навязывающего структуру, границы слоёв должны задаваться явно, иначе технические детали проникают в прикладную логику.

### Самостоятельная реализация инфраструктуры

Механизмы, которые обычно предоставляет фреймворк, реализованы в проекте вручную:

| Механизм | Реализация |
| -------- | ---------- |
| Внедрение зависимостей | `infrastructure/container` — `DIContainer`, аннотация `@Inject`, области видимости `Scope` |
| Маршрутизация HTTP | `infrastructure/http/router` — `Router`, `RouterScanner`, аннотации `@Controller`, `@Get`, `@Post`, `@Put`, `@Patch`, `@Delete` |
| Управление транзакциями | `application/transaction` + `infrastructure/persistence/transaction` — `TransactionManager`, `Propagation`, `IsolationLevel` |
| Валидация данных | `shared/validation` — базовые правила, валидация по аннотациям, комплексная валидация |
| Отображение ошибок в HTTP-ответы | `infrastructure/http` — `ErrorMapper`, `HttpStatusResolver`, `ErrorResponse` |

Это прямое следствие LC-03: самостоятельная реализация этих механизмов является учебной целью проекта. Одновременно это главный источник сложности системы, поэтому каждый такой механизм описан отдельно в разделе 8.

Готовые библиотеки используются там, где их самостоятельная реализация не даёт учебной ценности или создаёт неоправданный риск: HTTP-сервер (Jetty), пул соединений (HikariCP), миграции (Flyway), сериализация JSON (Jackson), хеширование паролей (BCrypt).

## 4.2 Декомпозиция верхнего уровня

**Слои первичны, предметные области вторичны.** Верхний уровень деления — слой; внутри слоя код делится по предметным областям (`task`, `project`, `planning`, `statistics`, `audit`, `user`).

Выбор сделан осознанно и служит QG-05: границы слоёв не дают прикладной логике срастись с техническими деталями, а деление по областям внутри слоя позволяет развивать области относительно независимо.

Подробная структура блоков описана в разделе 5.

## 4.4 Подходы к достижению целей качества

| Цель качества | Подход к решению | Статус | Подробности |
| ------------- | ---------------- | ------ | ----------- |
| **QG-01** — Конфиденциальность пользовательских данных | Каждая пользовательская сущность хранит ссылку на идентификатор владельца. Идентификатор пользователя извлекается из токена запроса. Фильтрация по идентификатору владельца выполняется на уровне запроса к БД, а не в прикладном коде — выборка физически не может вернуть чужие данные. | ⚠️ Запланировано | Раздел 8 |
| **QG-02** — Полезность AI-анализа | AI получает только данные текущего пользователя и только по своему явному запросу из закрытого каталога. Свободного доступа AI к системе нет (см. 4.5). | ⚠️ Запланировано | Раздел 8 |
| **QG-03** — Целостность игровой экономики | Изменение состояния задачи и операция с баллами выполняются в одной транзакции. Конкурентные изменения обнаруживаются через версионирование агрегатов (`VersionedAggregate`, `OptimisticLockException`) с повтором операции (`RetryableTransactionManager`). История операций с баллами (`points_history`) является источником правды для текущего баланса. | 🟡 Механизм готов, применение — нет | Раздел 8 |
| **QG-04** — Сохраняемость истории задач | Факты жизненного цикла задачи (выполнение, плановая и фактическая дата, переносы) записываются в отдельные append-only таблицы. Изменение текущего состояния задачи не перезаписывает эти записи. | ⚠️ Запланировано | Раздел 8 |
| **QG-05** — Поддерживаемость | Деление на слои с однонаправленной зависимостью (4.1) плюс деление по предметным областям внутри слоя (4.2). | 🟡 Слои реализованы; предметные области пока представлены только областью `user` | Раздел 5 |

**Обозначения статуса:** ✅ реализовано в коде · 🟡 реализовано частично · ⚠️ решение принято, кода нет.

### Общий механизм для AR-01 и QG-03

AR-01 (конкурентное изменение данных) и QG-03 (целостность баллов) решаются **одним механизмом** — оптимистичными блокировками поверх транзакций. Отдельного решения для каждой задачи не вводится.

Выбор в пользу оптимистичных блокировок опирается на профиль нагрузки системы: MILVIV — персональный инструмент, реальная конкуренция за одни и те же данные редка, поэтому пессимистичные блокировки создавали бы издержки без выигрыша.

## 4.5 Подход к интеграции с AI

Взаимодействие с Google Gemini строится по принципу **«AI возвращает данные, а не выполняет действия»**.

Команд пользователя нет: пользователь пишет свободный текст, намерение определяет AI.

1. Пользователь отправляет сообщение (например, «Хочу выучить английский»).
2. Если AI нужны данные пользователя, он **явно запрашивает** их из закрытого каталога. Сервер исполняет только разрешённые запросы — с фильтром по владельцу и проекцией полей.
3. AI возвращает **структурированное предложение**: создать, изменить или удалить цели, проекты, задачи, награды (или текстовый ответ, или уточняющий вопрос).
4. MILVIV валидирует предложение и показывает его пользователю. Для изменений и удалений показывается список затронутых сущностей (тип и название из БД), без деталей изменений.
5. Создания исполняются сразу, без подтверждения. Каждое изменение и удаление — **только при явном согласии** пользователя на эту операцию, иначе она отменяется. Создания и подтверждённые изменения исполняются каждое одной транзакцией.
6. После исполнения пользователь получает **отчёт**: какие сущности созданы, изменены, удалены или отменены, со ссылками на них, без деталей изменений. Отчёт строится по фактическому результату, а не по тексту AI.

AI может и отвечать на вопросы (например, делать анализ), и предлагать операции — в том числе в одном сообщении.

Доступ AI к данным:

* AI может запрашивать задачи, проекты, награды, рефлексии, планы и цели текущего пользователя. Статистику он вычисляет сам из задач и проектов;
* перед первым использованием пользователь **один раз** даёт согласие на использование своих данных; согласие хранится на сервере, без него AI недоступен и во фронтенде, и на сервере;
* **скрытые награды для AI не существуют**: он не может их прочитать, изменить или удалить и не знает об их существовании.

Чего AI не делает: не выполняет и не отменяет задачи (выполнение начисляет баллы и остаётся ручным), не обменивает баллы на награды, не меняет скрытость наград.

Следствия для архитектуры:

* AI не имеет прямого доступа к базе данных и не выполняет операций над сущностями;
* рамку задают сервер (каталог данных, белый список типов, лимиты) и подтверждение пользователя, а не формулировка запроса;
* ответ AI проходит ту же валидацию, что и данные, введённые пользователем вручную;
* AI получает только те данные, которые запросил и которые разрешил сервер, что обслуживает QG-01.

Подробно: [concepts/ai-assistant/](concepts/ai-assistant/README.md).

## 4.6 Организационные решения

| Решение | Обоснование |
| ------- | ----------- |
| Документация хранится в репозитории рядом с кодом | OC-02 — документация развивается вместе с системой |
| Архитектура документируется по шаблону arc42 | Позволяет быстро восстановить контекст после перерыва в разработке (раздел 1.3) |
| Секреты хранятся в `.env` вне репозитория | OC-01 — исходный код открыт |
| Схема БД версионируется миграциями Flyway | Схема изменяется только через миграции, история изменений схемы воспроизводима |
